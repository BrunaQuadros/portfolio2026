# Architecture

This file documents how the codebase is organized and where new files should go. Read this before creating any new file or folder.

## Architectural Principles

### Server Components by default
Use Next.js Server Components unless a component specifically needs browser APIs, local interactive state, event handlers, client-side hooks, or client-side animation. Add `"use client"` only at the smallest reasonable boundary, not at the top of a whole page.

### Composition over duplication
Before creating a new component:
1. Check if an existing one covers it
2. Check if composing existing components solves it
3. Check if an existing component just needs a new variant
4. Only create something new if it's a genuinely new, reusable pattern

### Component boundaries
Create a reusable component when the pattern repeats, is likely to repeat, represents a real design-system primitive, or meaningfully improves readability by being isolated. Don't create one just because a small block of JSX exists on its own.

### Keep page files lightweight
Route files (`page.tsx`) should mainly compose sections and reference data, not hold large amounts of styling or business logic directly.

## Current Folder Structure

- `app/` — pages and routes (Next.js App Router). Each folder here becomes a URL. `app/page.tsx` is the homepage, `app/layout.tsx` wraps every page
- `components/ui/` — components generated by ShadCN (Button, Card, etc). Base building blocks, customize via props/variants
- `components/` — custom components built using components/ui pieces and design tokens
- `lib/` — helper functions, types, constants (e.g. `lib/utils.ts`, generated by ShadCN)
- `public/` — static files: images, favicon, fonts if self-hosted

## Planned Site Map

- `/` — homepage
- `/about` — about me page
- `/case-studies/[slug]` — individual case study pages (roughly 3 planned)
- `/playground` or `/lab` — dump of older/experimental projects, less polished than case studies

Route naming decided while building the first case study (Faircado, 2026-08-24): `/case-studies/[slug]`.

## Content Architecture

Case study content should be structured data, not just hardcoded text scattered across page files. Example shape:

```ts
export type Project = {
  slug: string
  title: string
  description: string
  year: string
  role: string[]
  heroImage: string
}
```

This avoids duplicating the same project info across the homepage card, the case study page itself, and SEO metadata. Store this in `content/projects/` once the first case study is built.

## As the Project Grows

- `components/case-study/` — components specific to case study pages (e.g. CaseStudyHero, ImageBlock, QuoteBlock), once there's more than one case study
- `content/projects/` — structured project data, per Content Architecture above

## Naming Conventions

- Component files: PascalCase, matching the component name (e.g. `CaseStudyCard.tsx`)
- Utility files: camelCase (e.g. `formatProjectDate.ts`)
- Route folders: kebab-case (e.g. `app/case-studies/`)
- One component per file

## Import Aliases

- `@/components` instead of relative paths like `../../../components`
- `@/lib` for the same reason

## State Management

Prefer, in this order: server-rendered data → URL state → local component state → React context (only if genuinely shared across distant components) → external state library (should not be needed for a portfolio).

## Dependencies

Before adding any new package, check: does the platform already provide this? Would a small custom implementation be simpler? Does an existing dependency already solve it? Don't install something for a trivial problem. (See also CLAUDE.md's rule on not introducing new UI/CSS libraries without approval.)

## Off-Limits — Never Edit by Hand

- `node_modules/` — regenerated by `npm install`, disposable
- `.next/` — build output, regenerated automatically
- `package-lock.json` — managed by npm automatically

## Definition of Done

A piece of work isn't complete until:
- TypeScript passes with no errors
- Linting passes
- The production build succeeds
- Existing components were reused where appropriate, not duplicated
- No unnecessary new dependency was introduced
- Responsive behavior was checked
- Accessibility was considered (see ACCESSIBILITY.md)
- Relevant documentation was updated if this changed the architecture
